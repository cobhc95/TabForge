# TabForge Synth engine: handover for the next agent

Read this file first, then `README.md` (file map, signal flow, API). You do not need to read the rest of the TabForge app. Measurements and history: `docs/specs/TABFORGE_SYNTH_STATUS.md` (a log; skim only the section you touch).

## What this is
The owner wants their own, from-scratch, lightweight and extremely realistic General MIDI sound engine for TabForge, with guitar (especially distorted) as the showpiece. It is an SF2-compatible synth library plus modelled layers on top. It is a Sound engine choice "TabForge Synth (experimental)", never the default (Windows GM stays default). Everything must be genuinely ours: no third-party synth code, no third-party models or samples bundled without a clearly permissive licence. The owner judges by ear; you cannot listen, so you prove things with measurements and the owner's real recordings.

Layers (each can be switched via `Synth/SynthOptions.cs`; a menu generated from its descriptor table is planned):
1. SF2 playback (`Sf2/`, `Synth/`): spec-correct, the baseline for every program (drums, piano, strings, ...).
2. Guitar layer (`Guitar/`, programs 24-37): modelled string and pickup (DI), then amp, then optional cabinet. Default amp for programs 29/30 is the owner's captured amp (`Guitar/Amps/captured.nam`, NAM WaveNet lite) with a fitted 4-band output EQ; stage amp and clean-only are options; a user `.nam` and `.wav` cabinet override.
3. NAM runtime (`Nam/`): our own C# inference of the public Neural Amp Modeler format, including A2.
4. Humanizer (`Humanize/`): a window-based pass over the WRITTEN notes (not a streaming stage): structural dynamics, motif memory, fast-run model, strum model, position-keyed noise. Rules and numbers: `docs/specs/HUMAN_FEEL_SPEC.md` and the README.

## Unverified or risky (say so when you report)
Never run in the running app by a human; NAM A2 never run against a real A2 file (FiLM, groups, post-stack head, `.namb` unsupported -> falls back to the built-in amp); after a seek the humanizer's first 2 bars lack context; the realtime path has no delay compensation (not needed now that the humanizer has no look-ahead); the captured amp squeezes velocity 50-127 into ~1.5 dB at its output, as the owner's real amp does.

## How to work with the owner (follow this style)
- Be brief and plain. Lead with what is now true, then numbers, then caveats. Say plainly what is unverified. No jargon walls; bold labels and short lists are fine.
- They listen to ONE file per round: send a single combined WAV (`SendUserFile`) with everything on, no before/after pairs, no variants, unless they ask. Say in one line what it contains and what to listen for. Keep other files in the scratch folder.
- Ask before: downloading anything, installing anything, pushing, deleting data. Never push or tag. Commit each finished piece locally with no AI attribution.
- Token use is limited: you do the thinking, delegate expert work to one Opus agent at medium effort, cheap research to Haiku at high effort; one agent builds at a time; no full test suite; run long things in the background and do not poll.
- End each round with one decision question and two answers (for example "Drums or more tuning?"). Good questions to ask at the start: what did you hear in the latest demo and in which section; was the attack/peak problem fixed on all instruments; is the upper mid/EQ right now; are the strums and fast runs human enough; which instrument family matters most next; may the captured amp ship publicly.
- Their data: the clean DI and the same take through their real amp are in their Downloads folder (ask for the current paths). Private: analysis in Python, statistics only in the repo, no file names or song titles in any committed text.
